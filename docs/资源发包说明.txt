终末地伤害工作台资源发包说明

适用范围

本说明用于发布桌面版和手机版共用的正式数据、图片资源。
资源直接部署到国内、海外服务器，不再通过 GitHub Release 提供。


一、发包前需要准备什么

1. 一份完整的 Share Data JSON

必须是当前工具导出的完整 Share Data，里面应包含：

干员资料库
武器资料库
装备资料库
Buff 资料库
共享排轴资料

不要使用 max.json、buff.json 等早期拆分文件，也不要把单独的 SQLite 备份当作资源包输入。

2. 一份完整图片目录

图片必须与 Share Data 属于同一批资料，并包含所有被资料引用的干员、武器、装备及技能图片。

工具可以识别以下目录形式：

assets/images
images
直接以各图片分类目录作为根目录

即使本轮只修改了数据、没有修改图片，也仍然选择完整图片目录。工具会通过内容哈希判断图片是否真的发生变化。


二、两种发包方式

方式 A：直接交给 Codex（推荐）

你不需要自己打开打包工具，也不需要先生成 ZIP。

直接提供以下内容：

图片目录的本地绝对路径
一份完整 Share Data JSON 的本地路径，或直接上传该 JSON 文件
是否立即发布国内、海外

推荐发送格式：

图片目录：/Users/你的名字/Desktop/完整图片目录
Share Data：/Users/你的名字/Desktop/完整资料.json
请生成资源包并发布国内外，不走 GitHub Release。

路径中包含中文或空格没有关系。Codex 只处理明确指定的目录和文件，不会把桌面上的其他文件加入资源包。

Codex 会调用与浏览器打包工具相同的核心实现，因此生成规则、文件内容和校验逻辑一致；版本号中的时间以各自实际执行打包的时刻为准。


方式 B：自己在浏览器生成 ZIP

1. 确认本地开发服务器已经运行。

常用启动命令：

npm run dev

本地地址固定为：

http://127.0.0.1:3030/

如果服务器已经在运行，不要重复启动。

2. 打开资源打包工具：

http://127.0.0.1:3030/#/settings/resource-packager

3. 选择完整图片目录。

4. 选择唯一一份完整 Share Data JSON。

5. 点击生成并下载。

工具会自动完成：

校验 Share Data 格式
识别图片根目录
检查资料引用的图片是否齐全
标准化正式资料
计算数据和所有图片的 SHA-256
按实际打包日期、时间和内容哈希生成版本号
生成一个完整资源 ZIP

下载文件名称类似：

dmg-resource-release-20260812.143025.9d9efd499c53.zip

版本号中的日期和时间取实际打包时的北京时间。任何正式数据或图片发生变化，末尾的哈希也会变化。


三、怎样把资源交给 Codex

如果使用方式 A，只需提供图片目录和完整 Share Data，Codex 会负责生成资源 ZIP、验证并发布。

如果使用方式 B，浏览器生成 ZIP 后：

不要手工解压、修改或重新压缩资源 ZIP。
不要手工修改版本号、stable.json 或清单文件。
不要自行上传 GitHub Release。

直接把完整 ZIP 拖进 Codex，并发送：

发布这份资源，国内外一起部署，不走 GitHub Release。

如果浏览器因为重复下载给文件名增加了“(1)”等后缀，内容不会受影响，但建议只保留最终确认的一份，避免拿错文件。


四、Codex 会自动完成什么

1. 验证资源 ZIP 是否完整。

2. 验证版本号、数据 SHA-256、图片 SHA-256、图片引用和文件数量。

3. 将新版本与线上稳定版本比较。

如果内容根哈希完全相同，说明资料内容没有变化；除非明确要求重发，否则停止重复发布。

4. 将资源物化为服务器稳定通道和不可变版本目录。

5. 提交并推送本轮资源变更。

6. 从干净源码提交分别构建国内、海外产物，避免本地未跟踪文件污染构建结果。

7. 部署并验证国内服务器资源。

8. 部署海外 Sites，并验证海外独立图片交付。

9. 执行真实浏览器验收，包括：

桌面端首次安装
图片逐文件校验
离线冷启动
手机版最新数据加载
国内外资源版本一致性
缓存策略
Service Worker

10. 任意一路失败时停止发布或执行回滚，避免国内外长期处于不同版本。


五、怎样判断发布成功

Codex 的发布结果必须至少包含：

源码提交号
完整资源版本
数据版本
图片版本
海外 Sites 版本号
国内、海外正式访问地址
桌面端与手机版验收结果
国内、海外回滚点

国内外的 stable.json 必须指向同一个完整资源版本。

手机版必须读取线上最新版。

桌面版首次使用时可以自动安装正式资料；已有资料时，新版只下载并保存为带版本号的正式 Share Data，不得擅自覆盖用户当前正在使用的资料。


六、版本号怎样命名

完整资源版本格式：

日期.时间.内容哈希前12位

例如：

20260812.143025.9d9efd499c53

日期和时间来自本次实际打包时的北京时间，格式为 YYYYMMDD.HHmmss。

Share Data 的 exportedAt 只记录源资料何时导出，不再参与资源版本命名。

数据版本使用数据文件 SHA-256 的前 8 位。

图片版本使用全部图片路径、大小和 SHA-256 清单哈希的前 12 位。

哈希用于校验内容并识别相同资料。即使重发时日期和时间变化，相同内容的根哈希仍然相同。它属于内容级判重，不是 ZIP 内部的增量或分块存储去重。


七、出现问题时怎么处理

打包阶段报错：不要绕过校验，先修正缺失图片或错误 Share Data，再重新生成。

内容根哈希没有变化：说明输入内容与上一版相同，通常不需要重新部署。

日期或时间不符合预期：检查执行打包设备的当前时间和时区；正式版本一律按北京时间生成。

部署阶段失败：不要手工修改线上文件，交给 Codex 根据已保留的 Sites 版本和国内备份目录处理或回滚。

线上数据看起来没有更新：先核对 stable.json 的完整资源版本，再检查桌面端是否只是下载了新版但尚未由用户明确应用。


最简流程

推荐方式：

把完整图片目录地址给 Codex
把一份完整 Share Data JSON 给 Codex
说明“生成资源包并发布国内外”
等待打包、部署和验收结果

自行打包方式：

选择完整图片目录
选择一份完整 Share Data
点击生成 ZIP
把 ZIP 交给 Codex
等待国内外部署和验收结果
