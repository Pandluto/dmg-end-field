## 同文件双跑的口径

`tests/e2e/lts-dual-run.spec.ts` 只写一份动作和观察结构，依次运行：

- `3030`：原始 `v1.8-LTS@920a6f94`；
- `3040`：当前 `codex/v1.8-lts-slimming@1db30bc8`。

runner 在启动 Playwright 前核对监听 PID 的 cwd、branch、HEAD 和工作树状态。公共观察对象最后严格深比较；只有已声明的退役能力允许不同。

Hit 深层控件没有硬塞进双跑：原始 LTS 在这条全新测试数据路径下显示“暂无 Hit”，不存在可操作的公共 Hit 集合。Slim 已由候选 E2E 直接操作真实 Hit 并验证持久化；双跑继续比较两侧都存在的详情、伤害文本和目标抗性。这样保留了证据边界，没有用条件跳过制造假绿。

## 已确认但本轮没有修的风险

Equipment library 保存会依次写两个缓存 key，再执行持久化 flush。自动测试确认了两个具体场景：

1. 第一个 key 写成功、第二个 key 抛错时，第一个 key 已是新值，第二个仍是旧值；两份缓存会暂时不一致。
2. 两个 key 都写入内存后 flush 抛错时，当前页面能读到新值，但不能据此证明新值已经耐久落盘。

这不是“正常保存一定丢数据”，而是存储层在特定写入/flush 失败时缺少原子回滚合同。测试现在能稳定守住和暴露该事实；实现修复仍应作为独立 bug 处理，不能把“已测到”写成“已修好”。

## 剩余边界

以下内容不属于“瘦身代码已改却没有测试”的遗漏，而是现有本地三层测试无法代替的平台或穷举终验：

- 最终生产 Service Worker 接管后的真实断网冷启动、失败更新和回滚；
- 同一个真实浏览器 profile 从旧 LTS 升级到 Slim、再按既定方案回滚；
- 双标签 Web Locks/BroadcastChannel 的占用、主动接管和并发写入；
- SQLite 文件完整导出/恢复、损坏文件处理和开发侧恢复步骤；
- 操作系统原生文件选择器、下载实际落盘和 Electron 壳差异；
- 所有页面、所有主题、所有窗口尺寸的像素级截图穷举；
- 测试源码独立 strict `tsc` 门禁；当前生产源码 strict typecheck 已通过，测试由实际 runner 编译并执行。

因此，对“凡是瘦身改到的地方是否有全面测试”的准确回答是：**改动域已经全面闭环，足以支撑代码替代判断；平台终验和一个已被测试固定下来的 Equipment 原子性风险仍然独立存在。**
