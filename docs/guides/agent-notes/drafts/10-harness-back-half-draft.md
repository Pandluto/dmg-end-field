## 典型的垂直领域 Agent

垂直领域不是把 Agent 的名字换成游戏名词，也不是把通用 Agent 的 Prompt 写得更长。

它真正特殊的地方，是**同一类业务会反复发生，而且每次都落到真实产品状态上**。

今天有人要配装，明天还会有人要配装。每次的干员、队伍、现有装备和用户限制都不一样，模型选择的路线也可能不一样。

稳定的不是一句问题，也不是一条固定步骤。

稳定的是：

- 这到底是哪一项业务；
- 这项业务可以改变什么；
- 它需要哪些事实和知识；
- 当前阶段允许使用哪些能力；
- 做完以后，什么结果才可信。

在这个项目里，Workbench 里的真实工作大体可以分成五项：

| 业务 | 它负责的结果 |
| --- | --- |
| 选人 | 队伍成员与顺序 |
| 配装 | 武器、装备、技能等级与配置输入 |
| 排轴 | 技能按钮、动作顺序、位置与排轴结构 |
| BUFF | 按钮上的 BUFF、层数与相关战斗状态 |
| 计算统计 | 读取完整方案，计算、比较并解释结果 |

这里写的是当前重构方案要建立的边界，不是已经全部上线的运行事实。现有系统仍在等待把散落的旧规则解耦并迁入这套结构。

这里的划分不是为了凑五个 Harness。

它来自产品里五种不同的业务结果：它们改变的状态不同，完成条件不同，也应该能够独立更新。

角色名、装备名和“3+1”之类的术语只是目标或条件，不是新的 Harness。新增、删除、比较和预览只是业务里的动作，也不是新的 Harness。

## 先找“谁在负责”，再谈 Prompt

项目早期把业务规则写进 Prompt，没有错。业务还不稳定时，这是验证想法最快的地方。

问题出在同一条规则后来有了很多主人。

Workbench Prompt 讲一次，Host Prompt 再讲一次，Skill、Tool Description 和 Runtime 里又各留一份。

例如“应用配装前必须确认”，看起来只是一句话，实际可能同时经过：

- Prompt 是否要求模型先询问；
- Tool 是否允许进入写入；
- 审批有没有真正发生；
- 当前方案版本是否仍然一致；
- 产品最后有没有真的改变。

[Harness Handbook](https://ruhan-wang.github.io/Harness-Handbook/)把这种情况概括成 **One behavior, many implementation sites**：一个行为，会散落在多个实现位置。

问题因此不是“Prompt 太长”，而是：

> **同一个业务决定有多个主人，模型只能靠文本顺序猜谁说了算。**

所以这一次不再追求一份更完整的总 Prompt，而是先把边界分清：

| 边界 | 负责什么 |
| --- | --- |
| Host | 提供当前 Session、页面、checkout 和不能绕过的宿主事实 |
| Harness | 决定当前业务怎样理解目标、怎样使用能力、什么时候完成 |
| Knowledge | 提供带来源和适用条件的游戏知识 |
| Typed Tool | 声明并执行一个真实能力，返回结构化结果 |
| Product | 强制执行权限、审批、版本、公式和后置验证 |

同一条业务规则不应该为了“加强效果”，同时复制到 Prompt、Skill、Harness 和 Tool Description。

## 五项业务，不是五个文件

业务边界不能照着文件夹切。

例如一个排轴按钮里，既有技能和位置，也可能挂着 BUFF。排轴 Harness 可以决定按钮的顺序，BUFF Harness 可以决定按钮上的 BUFF；底层产品负责让两种状态保持一致。

如果按文件分权，它们马上又会踩在一起。

业务边界也不能照着一句话里的名词切。

“给这个干员配一套装备”里有干员、有装备，但用户要求的结果是配装，所以它属于配装业务。

“先换人，再配装，然后算一下”则是一个跨业务请求。

跨业务计划只记录先后顺序。每一步仍然交给自己的业务 Harness；它本身不是第六个万能 Harness。

这一步很重要。否则五项业务很快又会被塞回一套巨大的 Workbench Harness，之前的重复和冲突会重新出现。

## Harness 怎样接住一项真实业务

用户说：

> 给我干员搭配一套适合的装备。

系统首先要判断这是新配装、继续上一次确认，还是目标仍然不清楚。

确定业务以后，Harness 才进入这项真实工作：

```text
当前 Host 事实
→ 确定业务和目标
→ 绑定本次业务状态
→ 取得当前阶段需要的知识与 Context
→ 模型判断并使用允许的 Typed Tools
→ Tool Result 更新事实和阶段
→ 模型继续判断
→ 得到并验证真实结果
```

这不是一条要求模型逐字照做的固定 Workflow。

它表达的是几个不能混掉的边界：

- 事实先来自真实产品，不由模型编；
- 方法作为强参考进入 Context，不替模型做决定；
- Tool 是否可用，要服从当前业务和阶段；
- Tool Result 会改变下一轮判断所依据的事实；
- 写入是否成立，最后由产品硬合同验证。

模型仍然可以追问、比较多个方案、先读攻略或先查数据。

Harness 管的不是模型每一步必须怎么想，而是它处理这项业务时，**什么事实可信、什么方法可参考、什么能力可用、什么结果真的落地**。

## 知识不是第六个 Harness

游戏知识会贯穿五项业务，但知识本身不是一项业务。

配装时至少会遇到四类材料：

| 材料 | 来源 | 用来做什么 |
| --- | --- | --- |
| 当前事实 | checkout 与真实产品状态 | 看清干员、队伍和现有配置 |
| 游戏事实 | Catalog、技能数据与公式引擎 | 核对装备、数值和计算结果 |
| 策略知识 | 带来源和适用条件的攻略 | 形成候选并解释取舍 |
| 运行结果 | Tool Result | 把已经发生的事情带进下一轮 |

这四类材料不能互相冒充。

攻略可以解释为什么推荐某件装备，但不能改写 Catalog 里的装备数值。模型可以解释伤害结果，但不能替代真实公式。

也不应该把所有材料一次塞满。

[Anthropic 对 Context Engineering 的总结](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)指出，Context 是有限资源，关键问题不是“还能塞多少”，而是什么配置最可能产生需要的行为。

在垂直领域里，这件事会更具体：

> **当前业务、当前目标和当前阶段需要什么，就只把那部分知识带进来。**

## 版本化的不是“整个 Agent”

业务边界相对稳定，但解决业务的方法会持续变化。

配装方法变了，不应该要求重新发布选人、排轴、BUFF 和计算；也不应该要求用户为了使用新规则，重新建立整个 Session。

所以需要分清三件事：

- **业务定义**：这项业务可以改变什么，最多能使用哪些能力；
- **业务版本**：这一版怎样识别动作、组织阶段、读取知识和处理失败；
- **业务事务**：用户此刻正在做的那一件真实工作。

新事务可以使用最新业务版本。

已经进入“预览—确认—应用”的旧事务，则继续使用开始时的版本。否则用户确认时，背后的规则已经偷偷换掉，确认对象就不再是原来的方案。

这也是“可版本化”的实际意义：变化有位置，回退有边界，一项业务的修改不会把其他业务一起拖下水。

## Typed Tools 完成以后，长期迭代的是什么？

Typed Tools 稳定下来，只表示 Agent 的手相对稳定了。

之后还会长期变化：

- 怎样识别用户正在做哪项业务；
- 这项业务有哪些常见方法；
- 每个阶段需要什么知识；
- 哪些 Tool 此刻应该可见；
- 遇到歧义、纠正和失败时怎么办；
- 怎样解释结果，怎样判断工作已经完成。

这些才是垂直领域 Harness 真正要管理的内容。

[AI Harness Engineering](https://arxiv.org/abs/2605.13357)把能力放在“模型—Harness—环境”整体中讨论；[HarnessX](https://arxiv.org/abs/2606.14249)进一步尝试把 Harness 组成部分做成可组合、可根据运行轨迹演进的原语。

名称和实现都还在变化，但方向很一致：

> Agent 的进步不只来自换一个更大的模型，也来自把模型周围的工作条件组织得更清楚。

## 先停在这里

绕了一圈，Harness 仍然不是一份 Prompt，不是一张 Tool 列表，也不是把所有情况写死的巨大 Workflow。

对于这个项目，它更像一套围绕真实业务建立的求解环境：

- 业务边界告诉系统现在在解决什么；
- Knowledge 提供有来源的证据；
- Context 把当前需要的事实和方法交给模型；
- Typed Tools 提供真实能力；
- Runtime 与产品边界接住状态、审批和结果；
- 模型在这些条件里继续判断。

所以这篇最后想留下的是：

> **Harness 不替模型预先解完问题。它把一项真实业务需要的知识、状态、能力和边界组织起来，让方法成为非强制但强参考，让结果受到真实系统约束。**

至于运行轨迹怎样反过来改进业务版本，又怎样进一步形成自训练，留到下一篇再说。
