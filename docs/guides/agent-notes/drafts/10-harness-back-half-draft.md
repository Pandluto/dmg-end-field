## 典型的垂直领域 Agent

垂直领域不是把 Agent 的名字换成游戏名词，也不是在 Prompt 里多写一些专业术语。

它真正特殊的地方，是**同一类问题会反复出现，而且答案最终要落到真实领域里**。

今天有人问配装，明天还会有人问配装。每次的干员、队伍、现有装备和用户目标都不一样。

问题的名字相似，真正的解法却不能复制。

一个垂直领域 Agent 需要反复处理这些事情：

- 看懂用户真正想解决什么；
- 取得这一次问题所需的事实；
- 找到适用的领域知识；
- 选择能够产生真实结果的 Tools；
- 在运行中接收新信息并改变判断；
- 确认最后发生的事情和用户目标一致。

所以它与通用聊天 Agent 的区别，不只是“懂得更多”。

> **垂类 Agent 的“垂”，体现在它面对的问题边界、专业接口、知识来源、运行状态和验收方式上。**

一个领域里究竟有多少类业务、需要拆出多少个 Harness，不应该在文章里预先规定。它要根据问题怎样重复、状态怎样变化、能力怎样共享和结果怎样验证再决定。

## 垂直的不是名词，是问题边界

“干员”“装备”“武器”都是领域名词。

但只认识这些名词，还不能完成配装。

真正的问题是：

- 用户要优化什么；
- 当前队伍有什么限制；
- 哪些事实来自产品；
- 哪些建议来自攻略；
- 哪些结果需要真实计算；
- 用户要一份解释，还是要修改当前方案。

这些东西合在一起，才形成一类可以反复处理的问题。

所以 Harness 不应该按名词切，也不应该按文件夹切。

角色可以同时出现在配装、队伍分析和伤害解释里；一个 Tool 也可能被多种问题共享。

更合适的边界是：

> **哪些问题共享同一种目标、上下文、处理方法和完成判断？**

这个边界可以随着项目认识变深而继续调整，不需要先凑出一个固定数量。

## 先设计 Agent 使用的专业接口

专业人士不会只靠记忆工作。

程序员有编辑器、搜索、编译器和测试；化学家有文献库、分子工具和反应计算；游戏攻略作者也需要角色资料、装备数据、公式和真实方案。

[SWE-agent](https://arxiv.org/abs/2405.15793)把为模型设计的工作接口叫作 Agent-Computer Interface（Agent—计算机接口，ACI）。它发现，为模型提供简洁的文件查看、搜索、编辑和反馈格式，比直接扔给模型一套人类命令行更有效。

[ChemCrow](https://arxiv.org/abs/2304.05376)做的也是类似事情：模型不再凭语言猜化学事实，而是使用检索、分子转换和反应计算等专业 Tools。

这对垂类 Agent 的启发很直接：

> **不要只教模型怎样回答，要给它一套适合模型使用的专业工作台。**

Tool 需要有清楚的输入、输出、副作用和失败结果。

空结果也应该明确告诉模型“调用成功，但没有找到内容”，而不是让模型猜 Tool 是失败了，还是系统漏回了结果。

领域能力越专业，接口越需要替模型消除无意义的格式负担。

## 知识不能只是一大段资料

配装问题里可能同时出现几类材料：

| 材料 | 来源 | 用来做什么 |
| --- | --- | --- |
| 当前事实 | 真实产品状态 | 看清当前干员、队伍和已有配置 |
| 游戏事实 | Catalog、技能数据、公式引擎 | 核对对象、数值和计算结果 |
| 策略知识 | 带来源和适用条件的攻略 | 形成候选，解释为什么这样选 |
| 运行结果 | Tool Result | 把已经发生的事情带进下一轮 |

它们不能互相代替。

攻略可以解释为什么推荐某件装备，但不能改写 Catalog 里的装备数值。

模型可以解释伤害结果，但不能替代真实公式。

文字可以解释证据，不能代替证据。

垂类 Agent 的知识建设因此不只是做一个更大的知识库，而是说明：

- 这份知识来自哪里；
- 它适用于什么条件；
- 它解决什么问题；
- 什么情况下不应该使用；
- 新事实出现以后是否需要重新读取。

## Context 要随着问题变化

最简单的实现，是把所有资料一次塞进 Prompt。

但 Context 越长，不代表模型理解得越好。

[Anthropic 对 Context Engineering 的总结](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)把 Context 看成有限资源。真正的问题不是“还能放多少”，而是什么信息组合最可能让模型产生需要的行为。

同一个配装问题，在不同时间需要的 Context 也不同：

- 刚开始时，需要用户目标和当前方案；
- 判断装备是否存在时，需要 Catalog；
- 比较方案时，需要适用的攻略和公式事实；
- Tool 返回以后，需要新的真实结果；
- 用户修改条件以后，旧结论可能要失效。

所以 Context 不是一份永远不变的背景资料。

> **它是 Harness 在每一轮判断前，为当前问题重新准备的工作现场。**

方法可以进入 Context，作为模型的强参考；但它不应该偷偷变成一条唯一 Workflow。

## 状态不能只留在聊天里

真实业务经常跨越多个回合。

用户可能先要建议，再修改限制，接着确认某个候选，最后才决定是否应用。

如果目标、候选、证据和当前进度只存在聊天记录里，模型每一轮都要重新猜：

- 用户确认的是哪个候选；
- 候选依据的事实有没有变化；
- 哪些工作已经完成；
- 哪个 Tool Result 仍然有效；
- 当前是在探索、等待还是执行。

聊天记录适合帮助人理解过程，不适合单独承担业务状态。

需要继续使用的状态，应当有机器可读的身份和生命周期。它可以被恢复、比较、标记过期，也可以明确取消。

这不是为了替模型写死路线，而是避免模型靠自然语言回忆真实事务。

## 哪些应该写死，哪些不应该写死

不写死解法，不等于什么都交给模型。

有些东西适合保持开放：

- 先追问还是先查资料；
- 比较哪些候选；
- 怎样解释取舍；
- Tool Result 回来以后是否改变原判断。

有些东西必须由程序强制：

- 哪些 Tools 当前可以使用；
- 写入是否需要审批；
- 用户是否有权限；
- 数据版本是否仍然一致；
- 输入是否符合 Schema；
- 修改后是否满足真实产品条件。

可以把它理解成两层：

> **Harness 给模型方法和条件，产品边界决定什么动作真的可以发生。**

“非强制，但强参考”说的是模型怎样使用方法，不是说权限、审批和数据正确性也可以参考着办。

## 做对，不等于说得像对

普通问答经常根据最终文字评分。

真实 Agent 不能只这样评。

[τ-bench](https://arxiv.org/abs/2406.12045)让 Agent 在零售和航空等领域使用真实风格的 API 与政策，并根据最终数据库状态判断任务是否完成。

[PhysicianBench](https://arxiv.org/abs/2605.02240)把医疗任务放进真实 EHR 风格的环境，还为长流程设置了结构化检查点。

这些评测共同说明：

> **Agent 说“已经完成”不是完成，环境里出现正确结果才是完成。**

对垂类 Agent 来说，评测至少要看：

- 目标结果是否真的出现；
- 不该变化的内容有没有被误改；
- 领域规则和用户限制有没有遵守；
- 中间失败是否被正确处理；
- 同一任务重复运行是否稳定。

最终回答只是证据的一部分，不是唯一证据。

## Harness 到底管理什么

到这里，可以重新看最开始的配装问题。

Harness 不需要预先写出唯一配装答案。

它要管理的是：

- 当前正在解决什么问题；
- 这一轮模型应该看见哪些事实；
- 哪些知识可以作为方法参考；
- 模型能够使用哪些专业 Tools；
- 运行结果怎样进入下一轮判断；
- 状态怎样延续、失效和恢复；
- 最后怎样确认真实工作已经完成。

这些内容可以版本化，也可以继续增加和调整。

但文章不需要提前规定它们必须拆成几个业务、几个 Harness 或几个 Agent。

[AI Harness Engineering](https://arxiv.org/abs/2605.13357)把 Agent 能力放在“模型—Harness—环境”整体中讨论；[HarnessX](https://arxiv.org/abs/2606.14249)则尝试让 Harness 的组成部分能够组合，并根据运行轨迹继续演进。

具体名称和实现还会变化，但方向很清楚：

> **Agent 的进步不只来自更大的模型，也来自模型周围这套工作条件怎样被组织。**

## 先停在这里

垂类 Agent 不是背熟行业资料的聊天机器人。

它需要在一类真实问题里，持续取得事实、使用知识、调用专业能力、维护状态并验证结果。

Harness 不替模型预先解完问题，也不要求模型走唯一的路。

它把问题需要的知识、Context、Tools、状态和边界组织起来，让方法成为**非强制，但强参考**，让真实动作继续受到程序约束。

至于这些组成部分最终怎样注册、组合和版本化，又怎样根据运行经验继续改进，应该等项目给出更明确的工程边界以后再展开。
