# 1.8 LTS Slim 线上替代综合评估

- 评估日期：2026-08-04
- 未瘦身源码基线：`v1.8-LTS@920a6f94fc49fad0938a44b61009e349c217b6b8`
- Slim 候选：`codex/v1.8-lts-slimming@d6fc56867f8d39732f6b9e5b001b1595fca6097a`
- 当前 Sites 构建归档：`sites/main@902d57c78130d051187abbc191c2da0d53b006a9`
- 评估范围：功能、数据兼容、可维护性、产物体积、本机响应、依赖安全、工程规范、离线与发布回滚

## 结论

**Slim 能够代替当前未瘦身的线上代码，并且更适合成为今后唯一维护的 1.8 LTS 基线。**

但现在的准确发布结论是：**代码替代通过，立即无条件全量切换暂缓；完成一次数据升级/回滚与真实生产产物演练后即可上线。**

这不是因为还需要继续大规模瘦身，也不是因为已经测到主功能回归。相反，现有证据已经证明：

- Slim 完整包含 `v1.8-LTS` 的提交，未漏线上补丁；
- 两个分支用同一份黑盒浏览器测试执行保留功能，公共观察结果严格相等；
- Slim 的生产代码、重复页面代码、依赖、产物和调试日志都真实减少；
- Slim 的完整质量门禁通过，而旧 LTS 在 2026-08-04 的最新依赖审计下已经不能通过自己的高危门禁。
- Slim 的 Sites 专用生产构建也已通过，生成 37 个 atomic shell 文件；当前缺的是部署后的平台演练，不是构建能力。

上线前仍需关闭的核心问题只有两个：

1. **同一份真实浏览器数据的跨版本升级与回滚尚未实测。** Slim 写入的 Equipment `schemaVersion: 2` 在旧 LTS 回读时存在百分比再次换算的具体风险。
2. **最终生产产物尚未做一次真实 PWA/SQLite 发布演练。** Service Worker、SQLite 和双标签主体代码没有随瘦身改变，自动合同也通过，但真实断网冷启动、失败更新和旧产物回滚不能由本地开发服务器双跑代替。

完成这两项后，建议直接让 Slim 成为正式 LTS，不再长期双线维护未瘦身版和 Slim。

## 一、评估对象是否可信

### 1. 源码关系

本次不是拿两个不相干的版本做抽样比较：

- `git merge-base v1.8-LTS d6fc5686` 等于 `920a6f94`；
- Slim 完整继承 `v1.8-LTS`，没有 LTS 独有而 Slim 缺失的提交；
- Slim 在此基础上新增 96 个提交，内容包括瘦身、模块拆分、测试、依赖修补和若干缺陷修复。

因此，“线上补丁是否漏合并”这一类风险在提交关系上可以排除。

### 2. “当前线上版本”的身份边界

仓库里的 Sites 归档 `sites/main@902d57c7` 仍包含 Damage Sheet 和 ExcelJS，属于未瘦身一代。它与 `v1.8-LTS` 在 `7db0e5a6` 汇合；Slim 同时包含该线上源码和其后的 `b45ae2b5` 部署补丁。

但公开 [GitHub Releases](https://github.com/Pandluto/dmg-end-field/releases) 当前 latest 仍是 `v1.7.3`，没有一个 `v1.8` tag 能把“线上产物”与精确源码提交绑定起来。所以下线前应把现有线上包、其源码 SHA 和部署时间归档，不应只用“当前线上”这个口头名称作为回滚依据。

本报告以 `v1.8-LTS@920a6f94` 作为未瘦身源码基线，并用 `sites/main@902d57c7` 确认当前托管归档仍属于同一未瘦身产品代际。

## 二、功能能否替代

### 1. 同一份测试确实在两边运行

`tests/e2e/lts-dual-run.spec.ts` 不是两套相似测试，而是同一份黑盒合同依次操作：

- `3030`：`v1.8-LTS@920a6f94`；
- `3040`：`codex/v1.8-lts-slimming@d6fc5686`。

runner 会先校验监听进程的 cwd、worktree、branch、HEAD 和工作树状态。端口接反、旧进程或错误提交会在浏览器启动前直接失败。

本轮新鲜结果：

```text
v1.8-LTS 3030 -> v1.8-LTS@920a6f94, clean
v1.8-slim 3040 -> codex/v1.8-lts-slimming@d6fc5686, clean
1 passed (33.7s)
```

### 2. 双跑覆盖的公共能力

两侧在独立、全新的浏览器 context 中执行同样动作并比较同一数据结构，覆盖：

- 访问密码、首次资料安装、30 名干员、75 件武器、559 个图片资源；
- Operator、Buff、Weapon、Equipment、图片管理、Timeline、PPT 公共路由；
- 四类编辑器的创建、保存、刷新、分享与关键选择器；
- 五种主题下四类编辑器的关键结构、token、computed style 和核心交互；
- Timeline 选人、技能按钮、详情、伤害摘要、完整计算文本、PPT 元数据；
- OperatorConfig 可见性、BuffBatch 主流程和刷新后持久化；
- page error 与 console error 均为零。

公共 observation 最后使用严格深比较，不允许 Slim 仅仅做到“页面能打开”。

### 3. 明确允许不同的退役能力

下列差异属于产品已经确认的删除，不应被判成回归：

- Damage Sheet route；
- XLSX 导出和 ExcelJS；
- Timeline 中旧“表格”“伤害表”入口；
- 不工作的旧“计算侧栏”；
- Equipment 三件套重复 type 下拉；
- 三个相关页面里重复、容易写错的顶部 Buff 类型编辑入口。

普通装备保留的 select、双击 Buff 区域打开统一 Drawer、Timeline 伤害计算和 PPT 均继续存在。

### 4. 已知但不等价的行为

BuffBatch 在空 Timeline 时不再回退到全局按钮表，而是把 Timeline 的空数组视为权威结果。这个变化有独立测试，属于明确的新行为，不是测试遗漏。它不会影响正常已有 Timeline，但上线说明中不应把它描述成与旧 LTS 完全相同。

### 5. 双跑不能证明的部分

现有自动化仍不能把以下场景判为“已经全覆盖”：

- Canvas command queue 的 25 个回执分支真实投递；
- OperatorConfig 中装备槽、等级、固定属性、三件套的逐控件浏览器操作；
- SkillButton 全部 Hit、异常、抗性和单击/长按路径；
- BuffBatch 多按钮、多组、异常候选和全部键盘路径；
- 文件选择器、剪贴板 fallback、损坏分享文件和写入失败注入；
- 真实 Service Worker 断网恢复、失败更新和双标签争抢。

这些是测试覆盖边界，不是本轮已经发现的回归。主流程替代判断可以通过，但不能宣传成“每一个分支都被浏览器自动化证明”。

## 三、代码可维护性

### 1. 生产代码规模

统计口径为 Git 跟踪的 `src/**/*.{ts,tsx,css}`，排除相邻测试；行数使用标准换行计数。

| 指标 | v1.8-LTS | Slim | 变化 |
| --- | ---: | ---: | ---: |
| 生产 TS/TSX/CSS | 100,450 行 / 196 文件 | 91,337 行 / 228 文件 | -9,113 行（-9.1%），文件 +32 |
| TS/TSX | 69,462 行 / 167 文件 | 62,987 行 / 200 文件 | -6,475 行（-9.3%） |
| TSX | 39,696 行 | 26,655 行 | -13,041 行（-32.9%） |
| CSS | 30,988 行 / 29 文件 | 28,350 行 / 28 文件 | -2,638 行（-8.5%） |
| 平均 TS/TSX 文件长度 | 416 行 | 315 行 | -24.3% |
| 超过 2,000 行的 TS/TSX 文件 | 10 | 4 | -6 |

文件数增加并不表示变胖。大页面中的模型、公式、事务、持久化和分享边界被拆成较小模块，所以生产总行数下降的同时文件粒度更合理。

### 2. 关键页面本体

| 页面本体 | v1.8-LTS | Slim | 变化 |
| --- | ---: | ---: | ---: |
| Buff 编辑页 | 5,064 行 | 1,523 行 | -70% |
| Weapon 编辑页 | 3,734 行 | 1,710 行 | -54% |
| Equipment 编辑页 | 3,249 行 | 1,621 行 | -50% |
| Operator 编辑页 | 2,281 行 | 1,776 行 | -22% |
| BuffBatch 主组件 | 2,006 行 | 784 行 | -61% |

这些页面并非单纯把所有代码机械搬走：公共菜单、分享弹窗、工具按钮和工作簿样式开始复用；模型与事务模块不再依赖 React，能够独立测试。

需要诚实说明的是，按“页面加拆出的全部同域模块”计算，Weapon、Equipment、Operator 和 BuffBatch 的领域总代码并非全部减少。增加部分主要来自持久化合同、schema 兼容和可测试接口。Slim 的主要价值是**职责和风险可单独验证**，不是声称每一个功能域都用更少字符实现。

### 3. 测试资产

| 指标 | v1.8-LTS | Slim |
| --- | ---: | ---: |
| 相邻源码测试 | 10 文件 / 780 行 | 47 文件 / 7,298 行 |
| 浏览器测试与 helper | 0 | 3 文件 / 2,045 行 |
| 测试代码合计 | 10 文件 / 780 行 | 50 文件 / 9,343 行 |

Slim 已形成三层可复用证据：纯模型/存储合同、候选分支浏览器回归、基线/候选同套双跑。详情见 [可复用回归测试包](../testing/reusable-regression-suite.md)。

### 4. 仍有的维护债务

Slim 已经适合成为维护基线，但并非代码质量“毕业”：

- `CanvasBoard/index.tsx` 仍有 4,615 行；
- `browserTimelineStore.ts` 仍有 2,506 行；
- `OperatorConfigPage.tsx` 仍有 2,366 行；
- `SkillButton.tsx` 仍有 2,106 行；
- 新拆模块大多平铺在 `src/components` 根目录，后续按 `buff-draft`、`weapon-draft`、`equipment-sheet` 等功能目录归档会更清楚；
- Buff/Weapon persistence 仍有镜像式小实现，三个工作簿页面也还有相似 JSX；
- `MarkdownRenderer.tsx` 目前只有自身 CSS import，属于静态不可达候选；仓库还没有通用的 dead-code/CSS 可达性门禁。

这些都适合成为上线后的维护任务，不值得为了追求“绝对瘦完”继续推迟替代。

## 四、响应速度与产物

### 1. 生产构建体积

两侧分别执行生产构建后统计 `dist/assets`：

| 产物 | v1.8-LTS | Slim | 变化 |
| --- | ---: | ---: | ---: |
| JS raw | 3,150,971 B | 2,050,549 B | -34.9% |
| JS gzip | 945,963 B | 640,297 B | -32.3% |
| CSS raw | 636,069 B | 590,048 B | -7.2% |
| CSS gzip | 101,551 B | 95,195 B | -6.3% |
| 全部 `dist/assets` raw | 6,423,755 B | 5,277,312 B | -17.9% |
| 全部 `dist/assets` gzip | 3,022,051 B | 2,710,029 B | -10.3% |
| atomic shell 文件 | 40 | 37 | -3 |
| 入口 JS gzip | 121,609 B | 121,299 B | -0.25% |

最明确的收益来自：

- `exceljs.min`：936,594 B raw / 269,163 B gzip，Slim 中完全消失；
- Damage Sheet 的 JS/CSS chunk 完全消失；
- Buff 页面 JS：94,663 B raw / 23,857 B gzip 降至 45,673 B / 14,425 B；
- Weapon、OperatorConfig 和公共样式也有不同程度下降。

但官方资料、图片包和 SQLite WASM 没有因为代码瘦身显著变化，因此首次安装约 38 MB 资料时，代码体积不是主要耗时。

### 2. 本机浏览器响应采样

方法：Chrome headless、5 个全新隔离 context、两个目标交替顺序、本机开发服务器；数字为中位数。该采样只用于判断相对趋势，不能代表公网延迟或低端设备性能。

| 场景 | v1.8-LTS | Slim | 判断 |
| --- | ---: | ---: | --- |
| 打开、输入密码、到安装页 | 340 ms | 328 ms | 基本持平 |
| 下载本机资料并进入开始页 | 1,428 ms | 1,408 ms | 基本持平 |
| Buff 路由 | 52 ms | 54 ms | 基本持平 |
| Weapon 路由 | 98 ms | 96 ms | 基本持平 |
| Equipment 路由 | 37 ms | 43 ms | 基本持平 |
| Operator 路由 | 169 ms | 172 ms | 基本持平 |
| Timeline 路由 | 33 ms | 33 ms | 相同 |
| PPT 路由 | 28 ms | 28 ms | 相同 |

10 组样本均无 page error 或 console error。

结论是：Slim **减少了网络与解析负担，尤其是进入已退役/重页面相关代码路径时；但当前主流程的可感知响应没有出现数量级提升**。宣传时可以说“包更小、资源更少”，不能说“页面明显快一倍”。

单次本机生产构建耗时从约 2.95 秒降至 1.86 秒，方向上支持开发/发布更轻，但单样本不作为用户性能结论。

## 五、依赖、安全与工程规范

### 1. 依赖与审计

| 指标 | v1.8-LTS | Slim |
| --- | ---: | ---: |
| 直接运行依赖 | 9 | 8 |
| lockfile 包数量 | 702 | 616 |
| `npm audit` | 10（4 high、6 moderate） | 0 |
| 完整 `npm run check` | 审计阶段失败 | 通过 |

旧 LTS 的告警包括 ExcelJS → uuid，以及 brace-expansion、fast-uri、postcss、undici 等工具链传递依赖。高危项不都等于浏览器用户可直接利用，但它们已经使旧分支不能通过当前质量门禁；Slim 通过删除 ExcelJS并锁定已修补的传递版本关闭了这些告警。

### 2. 已经做到的规范

- 生产代码启用 TypeScript `strict`、unused locals/parameters 和 switch fallthrough 检查；
- 两侧生产 TypeScript 均通过；
- Slim 生产源码中 ExcelJS/XLSX 引用为零；
- 生产 `console.log/debug/info` 从 50 处降为 0，保留有意义的 warn/error；
- repository check 已加入退役 selector 防回归；
- 发布 workflow 固定 Node/npm 主版本、使用 lockfile、验证 tag/package 版本并生成 checksum；
- 双跑在执行行为断言前先锁定分支、提交和进程身份。

### 3. 仍缺的规范门禁

1. 默认 CI 和 release workflow 只执行 `npm run check`，其中不包含 Playwright 单分支 E2E 和双跑。
2. `tsconfig.json` 排除了 `src/**/*.test.ts(x)`，`tests/e2e` 也未进入独立 TypeScript 类型检查。
3. 两份 E2E 各自只有一个顶层长测试；前面失败会阻止后续场景，定位和并行能力一般。
4. 仓库没有 ESLint、Prettier、Knip、Madge 或通用重复代码检查，目前依靠 TypeScript 和自定义 repository check。

对本次发布，已经人工执行的 E2E 可以提供验收证据；对长期维护，至少应把单分支浏览器回归加入 CI，并给测试代码增加独立类型检查。

## 六、数据、离线与回滚风险

### 1. 正向升级风险较低

相对 LTS，以下核心平台代码没有变化：

- SQLite WASM 数据库与 schema；
- persistent local storage adapter；
- Service Worker 主体；
- Web Locks/BroadcastChannel 双标签协调；
- 设置页 SQLite 导出入口。

旧 schema normalize、Timeline bundle、编辑器保存/刷新和 SQLite archive conversion 都有合同；同套双跑也验证两侧可以在全新环境完成安装和主流程。因此，旧 LTS 数据升级到 Slim 的预期是正向兼容。

但当前双跑为两侧分别创建全新 context，不能证明“同一个 origin 上已有用户数据经过代码升级后仍完整”。必须用复制的真实 profile 或专用测试 profile 做一次原位升级。

### 2. 回滚旧 LTS 有具体 Equipment 风险

Slim 的 Equipment library 和 gear set 会写入 `schemaVersion: 2`，表示百分比数值已经是 canonical 值。Slim 回读时识别该标记，不再重复迁移。

旧 LTS 虽然可以忽略未知字段，但 normalize 不使用 library/gear-set 的 schema 2 标记，仍执行旧百分比启发式迁移。已有测试 fixture 证明下面的情况在 Slim 中必须保持：

```text
canonical value = 2
旧 raw 文本 = “20%”
Slim schema 2 回读后仍为 2
```

旧 LTS 回读同一对象时，可能因为 `value > 1` 再除以 100，得到 `0.02`。这不代表每一份装备数据都会损坏，但它证明“部署 Slim 后直接重新部署旧 LTS”不是已经安全的回滚方案。

上线前应二选一：

1. 修补并验证旧回滚产物，让它识别 schema 2；或
2. 把升级定义为单向迁移，先完整备份，并准备基于 Slim 的前向修复包，而不是回退到原始 `920a6f94`。

### 3. SQLite 备份能力没有完整用户闭环

[数据生命周期文档](../architecture/data-lifecycle.md)写着“选择备份、校验、替换数据库并重启应用”，但当前 `WebDatabase` 和设置页只有完整 SQLite 导出，没有普通用户可操作的完整 SQLite 导入恢复入口。

这是当前线上 LTS 也存在的能力/文档不一致，不是 Slim 新回归；但它削弱了发布回滚保障。若本次不补功能，至少应把发布说明改成“可导出，恢复需开发介入”，并实际演练开发侧恢复步骤。

### 4. PWA 和双标签

自动 `atomic shell` 检查通过，Slim shell 文件从 40 降到 37；Service Worker 和双标签主体代码相对 LTS 未改，所以代码层回归概率低。

本轮额外执行 `npm run build:sites`，Sites server/client 构建成功，随后 `check-atomic-service-worker.mjs dist/client` 返回 `ATOMIC_SW_OK`。这证明候选可以生成托管产物，但仍不等于浏览器已经经历真实的线上 Service Worker 更新。

仍需在最终生产构建上验证：

- Service Worker 接管后的断网冷启动；
- 新版本下载/校验失败时旧版本继续可用；
- 部署 Slim 后再部署回滚产物；
- 两个标签页的占用、主动接管和旧标签让出；
- SQLite 导出及恢复步骤。

Service Worker 激活新版本会清理旧 app-shell cache，所以回滚不能假设用户浏览器仍保留旧壳；必须保留并可重新部署旧构建产物。

## 七、上线建议

### 发布前硬门槛

1. **锁定身份**：推送候选，给当前线上产物和 Slim 候选分别记录 SHA/tag/checksum；保留旧静态包。
2. **做同源数据演练**：LTS 创建并保存 Timeline、四编辑库、图片和配置 → 升级 Slim → 修改并保存 → 验证正向读取；再执行计划中的回滚方式，重点检查 Equipment 百分比。
3. **做最终产物平台演练**：首次安装、已有数据启动、断网冷启动、失败更新、双标签接管、SQLite 导出/恢复。
4. **最终候选重新跑门禁**：

   ```bash
   npm run check
   npm run test:regression
   npm run test:regression:dual
   ```

### 替代后的维护动作

1. 将 Slim 重命名/合并为正式 1.8 LTS，旧 LTS 冻结为只读 tag，不再双线接补丁。
2. 把单分支 Playwright E2E 加入 CI；双跑只保留在迁移/瘦身封版流程。
3. 给源码测试和 E2E 增加独立 `tsc` 门禁。
4. 修正文档中的 SQLite 导入承诺，或补齐真实恢复入口。
5. 以后按风险继续拆 CanvasBoard、OperatorConfig、SkillButton；不把这些维护债务当成本次上线前继续大改的理由。

## 最终裁决

| 问题 | 回答 |
| --- | --- |
| Slim 能不能在功能上代替未瘦身线上版？ | **能。** 已覆盖的保留功能双侧严格相等，删除项均为有意退役。 |
| Slim 是否比线上版更容易维护？ | **是，明显更好。** 页面主体、生产 LOC、超大文件数量、依赖和调试噪声下降，测试边界大幅增强。 |
| Slim 是否明显更快？ | **包明显更小，主流程体感基本持平。** 不能夸大成显著交互提速。 |
| Slim 是否更规范、更安全？ | **是。** 当前完整门禁和依赖审计通过；但 E2E/测试类型检查还需进入 CI。 |
| 今天能否不做任何演练直接全量替换？ | **不建议。** Equipment 降级兼容和真实 PWA/SQLite 回滚尚未闭环。 |
| 是否还要继续一轮大规模瘦身再上线？ | **不需要。** 当前剩余主要是长期维护债务，不是替代阻断。 |
| 最合理的决策是什么？ | **把 Slim 定为唯一正式候选，完成一次跨版本数据与生产产物演练后替换线上，并停止双线维护。** |

## 本轮证据与限制

本轮实际执行或复核：

- 两侧 Git identity、merge-base、提交差异和远端状态；
- Slim `npm run check`；
- Slim `npm run build:sites` 及 Sites atomic shell 检查；

- Slim 单分支回归测试；
- `npm run test:regression:dual`；
- 两侧 production asset raw/gzip 统计；

- 代码规模、页面规模、测试规模、依赖树、CI/release、数据 schema 和回滚代码审查；
- 两份独立只读审查，分别聚焦维护规范与数据/发布风险。
