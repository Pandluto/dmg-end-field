# v1.8 LTS → slim 整棵树核验

- 核验日期：2026-08-03
- 原始基线：`v1.8-LTS@920a6f94fc49fad0938a44b61009e349c217b6b8`
- slim 基线：`codex/v1.8-lts-slimming@9e8d76e414abc952ab45ffa0e02d78795a76da89`
- 比较关系：两者 merge-base 正是原始 LTS 提交；slim 单向领先 87 个提交，原始 LTS 没有反向提交
- 核验原则：从完整 Git tree diff 重新出发，不把旧工作账本、旧审查结论或提交说明当作通过证据；只有直接测试、双侧测试或可证明的静态不可达性才能给出明确判定

## 结论

严格结论是：**常用功能和明确退役范围通过，但整棵树还不能判 100% 全部通过。**

当前没有在已覆盖的用户主流程里发现新的功能回归。Buff、Weapon、Equipment、Operator 四个编辑器的主要保存/刷新/分享流程，Timeline、SkillButton 详情、BuffBatch 主流程、PPT 报表，以及五种主题下四个编辑器的公共观察结果，都已经实际运行通过。Damage Sheet、XLSX、ExcelJS、无效“计算侧栏”等退役项也有双侧窄白名单证明。

不能全过的原因不是门禁失败，而是完整 diff 中仍有以下事实：

1. `CanvasBoard` 的命令回执外壳覆盖 25 个显式 `command.op` 分支，但没有真正投递命令队列的直接测试。
2. OperatorConfig 的共享装备计算合同有测试，真实页面里的装备选择、等级、固定属性和三件套展示没有浏览器断言。
3. BuffBatch 空 Timeline 从“回退全局按钮表”改为“权威空数组”；新行为有测试，但它是 `TESTED-CHANGE`，不是与 LTS 等价。
4. PPT 工具栏发生真实几何变化，非编辑器页面的主题视觉和不刷新实时切主题没有直接验证。
5. 共享分享对话框、文件选择器、剪贴板 fallback、复杂编辑器次级控件和部分失败路径只有局部或间接覆盖。
6. Equipment 成功保存与 revision 有测试，但连续写两个 key 时的第二次写入/flush 失败没有回滚合同，存在半保存风险；本轮只记录，不修复。
7. 双跑脚本本身只检查端口可访问，不校验服务对应的 Git 提交；本次人工核对过进程目录，所以本次结果可信，但自动化仍可能误复用错误服务器。

因此，当前可以说“主功能可用、已测范围相等、瘦身收益成立”，不能说“所有差异都有测试且全部等价”。

## 判定口径

| 判定 | 含义 |
| --- | --- |
| `PASS-DUAL` | 同一黑盒流程在原始 LTS 与 slim 两侧运行，公共观察对象严格相等 |
| `PASS-DIRECT` | slim 上有直接模型、服务或浏览器合同并实际通过，但不是同一可执行测试在两棵树上运行 |
| `EXPECTED-REMOVAL` | 产品明确退役；双侧测试要求 LTS 存在、slim 不存在，或调用图证明原代码不可达 |
| `TESTED-CHANGE` | 与 LTS 行为不同，新行为有直接测试；不得冒充等价 |
| `PARTIAL` | 主路径有测试，但同一变更域仍有未覆盖分支 |
| `UNTESTED` | 没有能直接证明该差异的测试 |
| `STATIC` | 仅能通过依赖、调用图、选择器或源码检查确认，不是行为测试 |
| `CONCERN` | 发现真实风险或基础设施缺口，但本轮没有把它修成已验证缺陷 |

## 双跑能证明什么、不能证明什么

双跑的优点是白名单很窄：公共 observation 使用严格深比较，只有以下五项允许不同：

1. Damage Sheet route
2. XLSX 导出
3. Toolbar “表格”
4. Workbench “伤害表”
5. 无效“计算侧栏”

它已经可靠证明两侧被观察到的登录、安装、公共 route、四编辑器主流程、Timeline、伤害文本、PPT、OperatorConfig 可见性、BuffBatch 主流程和错误集合相等。

但它不能把未观察的行为自动变绿。尤其是 Canvas command queue、OperatorConfig 深层表单、PPT 几何、非编辑器主题、异常持久化和分享 fallback。

### 身份门禁已关闭

最终封版已让 `run-lts-dual-e2e.mjs` 在 Playwright 启动前自动完成以下检查：

- 两个 URL 必须指向本机服务，并各自只有一个监听进程。
- 通过监听 PID 的 cwd 读取真实 Git worktree、branch 和 HEAD。
- 3030 必须与本机 `v1.8-LTS` worktree 完全一致；3040 必须与当前 `codex/v1.8-lts-slimming` worktree 完全一致。
- 无论复用已有服务还是自动启动 3030，身份不符都会在浏览器测试前直接失败，并打印期望值与实际值。

反向验证中故意交换 3030/3040，runner 在 0.2 秒内准确报告“期望 `v1.8-LTS@920a6f94`，实际收到 `codex/v1.8-lts-slimming`”，退出码为 1；恢复正确端口后，同套双跑为 `1 passed (30.9s)`。至此错误服务器得到假绿的基础设施缺口已经关闭。

`npm run check` 仍不直接包含双跑，因为它需要同时运行两棵工作树；封版流程明确把两侧 `npm run check`、3040 细测和独立双跑列为四项门禁。

## 后续独立质量验收顺序

双跑身份校验和瘦身封版已经完成。后续若要继续关闭未观察分支，不应只重复现有双跑；重复运行不会扩大覆盖面。建议顺序是：

2. 为 OperatorConfig 增加真实装备选择、等级、fixedStat、三件套 UI 浏览器测试。
3. 明确 BuffBatch 空 Timeline 是接受的新语义，还是必须恢复 LTS fallback；按决定增加双侧/变更合同。
4. 为 Equipment 双 key 保存失败补原子性测试；本轮先不修实现。
5. 补 PPT 几何和非编辑器主题的 computed-style 或截图对比。
6. 补共享 Dialog 次级交互、clipboard fallback、Buff/Weapon 异常保存和 Operator 复杂控件。
7. 每一批独立工作完成后，再跑完整两侧门禁、3040 详细 E2E 和固定 3030/3040 双跑。
