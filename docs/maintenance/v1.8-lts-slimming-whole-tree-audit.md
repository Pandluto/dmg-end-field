# v1.8 LTS → slim 整棵树核验

- 核验日期：2026-08-03；补测闭环：2026-08-04
- 原始基线：`v1.8-LTS@920a6f94fc49fad0938a44b61009e349c217b6b8`
- slim 补测候选：`codex/v1.8-lts-slimming@1db30bc83a2d3ece31704c762b4b2a1a7ddb8da1`
- 比较关系：两者 merge-base 正是原始 LTS 提交；slim 单向领先 99 个提交，原始 LTS 没有反向提交
- 核验原则：从完整 Git tree diff 重新出发，不把旧工作账本、旧审查结论或提交说明当作通过证据；只有直接测试、双侧测试或可证明的静态不可达性才能给出明确判定

## 结论

严格结论是：**瘦身改动域的测试已经闭环，足以支持替代验收；平台终验和一个已确认的 Equipment 原子性风险仍不能写成 100% 消失。**

2026-08-04 的补测把上轮明确列出的代码覆盖缺口逐项关闭：Canvas command queue 真实成功/错误投递、OperatorConfig 装备/等级/三件套、BuffBatch 次级路径、PPT 几何、实时五主题、共享 Dialog/file picker/clipboard fallback、Operator 技能/Hit/Buff 深层编辑、Weapon 右键菜单以及 Buff/Weapon/Equipment 持久化失败路径都已有直接或双跑证据。

当前没有在这些用户流程里发现新的瘦身回归。Damage Sheet、XLSX、ExcelJS、无效“计算侧栏”等退役项继续由双侧窄白名单保护。完整补测矩阵见 [v1.8 LTS Slim 补测闭环](../testing/v1.8-lts-slimming-test-closure.md)。

仍需诚实保留三类边界：

1. BuffBatch 空 Timeline 是有测试的新语义，不与旧 LTS 冒充等价。
2. Equipment 第二次 key 写入失败会形成新旧缓存并存，flush 失败也没有回滚；自动测试已稳定证明风险，但本轮没有修改产品实现。
3. 真实 Service Worker 断网/回滚、同 profile 跨版本升级、双标签并发、SQLite 文件恢复和 OS/Electron 行为属于平台终验，不由本地 Node/Playwright 双跑代替。

因此，当前可以说“凡是瘦身改到的代码域都有验收证据”，但不能把平台场景、所有输入组合和所有像素也声称为穷举通过。

## 判定口径

| 判定 | 含义 |
| --- | --- |
| `PASS-DUAL` | 同一黑盒流程在原始 LTS 与 slim 两侧运行，公共观察对象严格相等 |
| `PASS-DIRECT` | slim 上有直接模型、服务或浏览器合同并实际通过，但不是同一可执行测试在两棵树上运行 |
| `EXPECTED-REMOVAL` | 产品明确退役；双侧测试要求 LTS 存在、slim 不存在，或调用图证明原代码不可达 |
| `TESTED-CHANGE` | 与 LTS 行为不同，新行为有直接测试；不得冒充等价 |
| `PARTIAL` | 主路径有测试，但同一变更域仍有未覆盖分支 |
| `UNTESTED` | 没有能直接证明该差异的测试 |
| `STATIC` | 仅能通过依赖、调用图、选择器或源码检查确认，不是行为测试 |
| `CONCERN` | 发现真实风险或基础设施缺口，但本轮没有把它修成已验证缺陷 |
| `CONFIRMED-CONCERN` | 自动测试能稳定证明风险场景与当前行为，但实现尚未修复 |

## 双跑能证明什么、不能证明什么

### 身份门禁已关闭

最终封版已让 `run-lts-dual-e2e.mjs` 在 Playwright 启动前自动完成以下检查：

- 两个 URL 必须指向本机服务，并各自只有一个监听进程。
- 通过监听 PID 的 cwd 读取真实 Git worktree、branch 和 HEAD。
- 3030 必须与本机 `v1.8-LTS` worktree 完全一致；3040 必须与当前 `codex/v1.8-lts-slimming` worktree 完全一致。
- 无论复用已有服务还是自动启动 3030，身份不符都会在浏览器测试前直接失败，并打印期望值与实际值。

反向验证中故意交换 3030/3040，runner 在 0.2 秒内准确报告“期望 `v1.8-LTS@920a6f94`，实际收到 `codex/v1.8-lts-slimming`”，退出码为 1；恢复正确端口后，同套双跑为 `1 passed (30.9s)`。至此错误服务器得到假绿的基础设施缺口已经关闭。

`npm run check` 仍不直接包含双跑，因为它需要同时运行两棵工作树；封版流程明确把两侧 `npm run check`、3040 细测和独立双跑列为四项门禁。
